# Status

The claims pilot in `docs/PLAN.md` is built: all six phases are done. The harness in `docs/PLAN_HARNESS.md` is built: all five phases are done. The refactor in `docs/PLAN_REFACTOR.md`, which answers the human review in `docs/HUMAN_REVIEW_HARNESS.md`, is built: all six phases are done.

## Running it

- `npm run dev` starts the backend on port 8000 and the dashboard on http://localhost:5173. `UNDERCOVER_API` points both the dashboard and the agent at a backend elsewhere, such as `http://127.0.0.1:8002`.
- `uv run -m backend.seed` rebuilds the database from `data/`, putting every claim back in the queue. Run it after pulling a build that changes the database, such as this one.
- `uv run -m agent` starts a run: the queue agent works every waiting claim, printing a line for each, then a summary for the handlers. `uv run -m agent --cap 5` works at most five claims and leaves the rest waiting. `uv run -m agent CLM-1001` works one claim and prints its line, such as `CLM-1001  approve  $420.00`, or what went wrong. All three use the real model through OpenRouter.

## Built

- `backend/`: SQLite database seeded from `data/` (never `data/evals/`), at `undercover.db` or the path in `UNDERCOVER_DB`, created on startup when missing. The policy wording and the claims manual are stored as numbered sections, split at their `## ` headings. Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `list_handlers`, `list_steps`, `get_instructions`, `list_sections`, `read_section`. Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `sign_off_claim`, `fail_claim`. A claim moves from waiting to in progress to decided, or to waiting for sign-off when an approval pays over the limit in `company.json`. `pay_claim` refuses such a payout with a 403 until a handler signs off, and signing off pays it. `fail_claim` records a failed attempt on a claim in progress as an `error` step and sends it back to waiting, or to left for a handler on its second failure. Run operations: `start_run`, `write_todos`, `finish_run` and `get_current_run`. A run holds its cap, its to-do list (each item to do, in progress, done or left for a handler) and its summary. Starting a run fails any claim a stopped run left in progress. One `fetch_one` helper answers every "find this row or return 404", and one `claim_in` helper every "this claim must be in this state or return 409". The agent's instructions are in `backend/instructions/`: `queue.md` for running the queue and `claim.md` for working a claim, each written as a goal, what the agent has to work with and its limits. `get_instructions` serves both. A test checks that every operation follows the API rules.
- `agent/`: four modules, with imports running one way: `__main__` to `harness`, `harness` to `tools` and `api`, `tools` to `api`. `api.py` holds the backend's address (`UNDERCOVER_API`, or port 8000) and one function per backend operation, raising `ApiError` for a refusal and `ApiUnavailable` for a lost connection or a server error. `tools.py` holds every tool for both agents and their contexts. The claim agent's seven tools, `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `read_section`, `record_decision` and `pay_claim`, get the claim, policy and customer from `ClaimContext`, so the model can't name another claim. The queue agent's three tools, `list_claims`, `write_todos` and `work_claim`, get the run from `RunContext`, which reserves each claim against the cap under a lock, so parallel hand-overs can't pass it. `harness.py` holds the model, the middleware both agents share and one streaming function. `run_claim_agent(claim_id, thread_id)` records every tool call, tool result and message as a step, and each section it reads as a `read` step. `work_claim(claim_id)` reports the outcome in one line, sends a claim that fails before its decision to `fail_claim`, and pays an approval within the limit that was left unpaid. `work_queue(cap)` runs the queue agent with its cap, its reminders of missed claims and its summary. `__main__.py` is the command line. LangChain middleware gives refusals to the model (`ToolErrorMiddleware`), retries a failed model call up to 3 times, retries a lost backend call up to twice for every claim tool and for `list_claims` and `write_todos` (never for `work_claim`), and stops a claim attempt after 30 model calls. Model calls time out after 60 seconds. The default model is `deepseek/deepseek-v4.1-flash` with low reasoning effort.
- `dashboard/`: the queue (`/`), with counts by state, including Left for a handler, the current run's to-do list and summary, and a line per claim. A claim in full (`/claims/:claimId`), with its policy, earlier claims, the decision and payment, the agent's steps as it works, including the sections it read and any failed attempts, and a sign-off form for a held payout. The agent's instructions for running the queue and for working a claim (`/instructions`), read only. The queue and a claim page refresh every two seconds. Styled to `BRAND.md` in light and dark mode.
- `e2e/`: tests of the three pages, the agent's steps appearing on a claim page, a handler signing off a held payout, and a run's to-do list filling in on the queue page. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, and its own dashboard on port 5174, so it can run next to `npm run dev`.

## Review of the backend and dashboard

The refactor applied the human review's questions to `backend/` and `dashboard/` as well.

- Fixed in the backend: six copies of "find a row or return 404" became `fetch_one`, four copies of "the claim must be in this state" became `claim_in`, the base fields of a claim are built once, every model is built from a row the same way, and the routes that return a claim reuse `get_claim`.
- Fixed in the dashboard: Read and Result steps share one folded layout, the to-do chip sits with the other chips, the list of states comes from the same list as the `Status` type, and a failed request with no body shows "The request failed" instead of a parsing error.
- Fixed across both: the agent reads the backend's address from `UNDERCOVER_API`, the dashboard's setting, instead of a fixed address.
- Kept, with reasons: the status names in SQL, because every response is checked against the `Status` type; `settle` in the harness, because paying stays a separate backend operation that enforces the limit and the amount; and `work_claim` catching every error, because one bad claim must never stop a run, and the error is recorded on the claim.

## Known limitations

- One run at a time. Starting a run fails every claim in progress, so a second run started while another is working would fail that run's claims. Fixing it needs claims linked to the run that started them.
- The decisions have not been scored against the handlers' decisions in `data/evals/`.

## Last live runs

On November 11, 2026, after the refactor and a reseed, `uv run -m agent` with no cap worked all 25 claims in 9 minutes 19 seconds, for $0.11 of OpenRouter usage: 15 approve, 5 decline and 5 refer. All 12 approvals within the limit were paid exactly their payout, $4,720.00 in all, and the 3 over $1,000 (CLM-1003 for $3,750.00, CLM-1008 for $2,240.00 and CLM-1011 for $1,150.00) wait for sign-off with no payment. No claim failed or was left for a handler, and none is in progress. Each claim agent read 8 to 16 sections, 318 in all. These decisions have not been scored against `data/evals/`.

On November 11, 2026, after the refactor and a reseed, `uv run -m agent --cap 5` with `deepseek/deepseek-v4.1-flash` worked five claims on its own in 1 minute 44 seconds and left the other 20 waiting, with none in progress. It made the same decisions as the trial before the refactor: CLM-1001 approved for $420.00 and paid once, CLM-1008 for $2,240.00 and CLM-1011 for $1,150.00 approved and waiting for sign-off with no payment, CLM-1018 referred and CLM-1010 declined. Each claim agent read 12 to 14 sections, shown as Read steps on its claim page, and the summary was one plain paragraph. A later one-claim run called a paid $420.00 approval "waiting for sign-off" in its summary, so the queue instructions now say what that ending of a claim's line means; the next run's summary was right. Codex then reviewed the refactored code with the review prompt in `community_contributions/erfan_hesami/week1day5_codex_review/`: of the human review's eight issues, it found five fixed and three partly remaining (the harness still mixes in UnderCover's workflow, the shared `started` list, and the detail in the instructions).

On November 10, 2026, before the refactor, three trials of `uv run -m agent --cap 5` decided the same five claims in the same way, and `uv run -m agent CLM-1020` approved $240.00 after reading the manual's interpretation notes on wild animals.

On September 27, 2026, the pilot's `uv run -m agent` with `openai/gpt-6-luna` worked all 25 claims in 2 minutes 47 seconds: 17 approve, 5 decline and 3 refer.
