## Running it

- `npm run dev` starts the backend on port 8000 and the dashboard on http://localhost:5173.
- `uv run -m backend.seed` rebuilds the database from `data/`, putting every claim back in the queue. Run it after pulling a build that changes the database, such as this one.
- `uv run -m agent` starts a run: the queue agent works every waiting claim, printing a line for each, then a summary for the handlers. `uv run -m agent --cap 5` works at most five claims and leaves the rest waiting. `uv run -m agent CLM-1001` works one claim and prints its line, such as `CLM-1001  approve  $420.00`, or what went wrong. All three use the real model through OpenRouter.

## Built

- `backend/`: SQLite database seeded from `data/` (never `data/evals/`), at `undercover.db` or the path in `UNDERCOVER_DB`, created on startup when missing. The policy wording and the claims manual are stored as numbered sections, split at their `## ` headings. Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `list_handlers`, `list_steps`, `get_instructions`, `list_sections`, `read_section`. Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `sign_off_claim`, `fail_claim`. A claim moves from waiting to in progress to decided, or to waiting for sign-off when an approval pays over the limit in `company.json`. `pay_claim` refuses such a payout with a 403 until a handler signs off, and signing off pays it. `fail_claim` records a failed attempt on a claim in progress as an `error` step and sends it back to waiting, or to left for a handler on its second failure. Run operations: `start_run`, `write_todos`, `finish_run` and `get_current_run`. A run holds its cap, its to-do list (each item to do, in progress, done or left for a handler) and its summary. Starting a run fails any claim a stopped run left in progress. The agent's instructions are in `backend/instructions/`: `queue.md` for running the queue and `claim.md` for working a claim. `get_instructions` serves both. A test checks that every operation follows the API rules.
- `agent/`: `run(claim_id, thread_id)` starts the claim, fetches its instructions from the backend and works the claim with seven tools named after backend operations: `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `read_section`, `record_decision` and `pay_claim`. It records every tool call, tool result and message as a step, and each section it reads as a `read` step. LangChain middleware retries a failed model call up to 3 times and a failed backend call up to twice, and stops an attempt after 30 model calls. Model calls time out after 60 seconds. `work_claim(claim_id)` runs it on a new thread and reports the outcome in one line. It sends a claim that fails before its decision to `fail_claim`, and pays an approval within the limit that was left unpaid. The queue agent in `agent/queue.py` works a run with three tools: `list_claims`, `write_todos` and `work_claim`, which hands one waiting claim to `work_claim` and refuses once the run has started as many claims as its cap. When the queue agent replies while waiting claims remain within its cap, the harness reminds it, at most twice. Its last reply is the run's summary. If the queue agent itself fails, the run finishes with a summary saying why. The default model is `deepseek/deepseek-v4.1-flash` with low reasoning effort.
- `dashboard/`: the queue (`/`), with counts by state, including Left for a handler, the current run's to-do list and summary, and a line per claim. A claim in full (`/claims/:claimId`), with its policy, earlier claims, the decision and payment, the agent's steps as it works, including the sections it read and any failed attempts, and a sign-off form for a held payout. The agent's instructions for running the queue and for working a claim (`/instructions`), read only. The queue and a claim page refresh every two seconds. Styled to `BRAND.md` in light and dark mode.
- `e2e/`: tests of the three pages, the agent's steps appearing on a claim page, a handler signing off a held payout, and a run's to-do list filling in on the queue page. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, and its own dashboard on port 5174, so it can run next to `npm run dev`.

## Last live runs

On November 10, 2026, after reseeding, `uv run -m agent --cap 5` with `deepseek/deepseek-v4.1-flash` worked five claims on its own in 3 minutes 15 seconds, and left the other 20 waiting. The queue agent chose the five oldest by submission date and planned them as a to-do list, which the queue page showed filling in and being ticked off. The run approved CLM-1001 for $420.00, which was paid. It approved CLM-1008 for $2,240.00 and CLM-1011 for $1,150.00, which wait for sign-off with no payment, referred CLM-1018 and declined CLM-1010. Each claim agent read 7 to 13 sections of the wording and the manual, shown as Read steps on its claim page. No claim failed. Two earlier trials that day decided the same five claims in the same way, in 91 and 124 seconds. They led to two changes to the queue instructions, so that its summary is one plain paragraph for the handlers and a referral is not described as left for a handler. These decisions have not been scored against the handlers' decisions in `data/evals/`.

The same day, `uv run -m agent CLM-1020` worked one claim in 48 seconds. It read four sections of the wording and five of the manual, including the interpretation notes on wild animals, and approved $240.00, which was paid.

On September 27, 2026, the pilot's `uv run -m agent` with `openai/gpt-6-luna` worked all 25 claims in 2 minutes 47 seconds: 17 approve, 5 decline and 3 refer.
